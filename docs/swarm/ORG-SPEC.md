# 蜂群组织规格 v1.0

## 零、与本项目既有机制的关系

本规格不是新发明，是 `kernel.md` 九条生成链在**开发侧**的实例化：

| kernel 机制 | 本规格中的体现 |
|---|---|
| §2 L-REFORM 随时重建 | 组织规格与产物分离——换编排器不丢产物，产物不依赖任何 agent 存活 |
| §3 I-DISC 判别器独立 | L2 判别器必须是 fresh 上下文，不与生成者同会话 |
| §4 只认产物不认对话 | 全部交付落盘为文件；对话中的结论一律不算数 |
| §5 状态只能由产物跃迁 | 批次状态由 git commit 与校验器输出定义，不靠声明 |
| §6 触点极简 | **4 个检查点**，且只有含不可逆维度的决策点上升 |
| §7 死法预演 | §六 死法与对策 |
| §10 goal-keeper | 不可委托裁决的四类事项已列 §三 |

```
                    ┌──────────────────────────────────┐
                    │  goal-keeper（人 / 学习者）          │
                    │  · 目标锚：学什么、什么算学会         │
                    │  · 不可委托裁决（§三）                │
                    │  · 判定门最终授权                     │
                    └────────────────┬─────────────────┘
                                     │ 成军授权 / 批次契约
                                     ▼
                    ┌──────────────────────────────────┐
                    │  swarm-orchestrator（父会话 = mavis） │
                    │  · 唯一文件所有权分配者              │
                    │  · 批次契约签发与回收                │
                    │  · 跨文档修正的唯一执行者             │
                    │  · 记忆三分区（§四）                 │
                    └────────────────┬─────────────────┘
             ┌───────────────────────┼───────────────────────┐
             ▼                       ▼                       ▼
    ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
    │ domain-agent A  │     │ domain-agent B  │     │ domain-agent C  │
    │ 批次 9 数据流    │     │ 批次 8 界面      │     │ 批次 6 权责追溯  │

    └────────┬────────┘     └────────┬────────┘     └────────┬────────┘
             └───────────────────────┼───────────────────────┘
                                     ▼
                    ┌──────────────────────────────────┐
                    │  verifier-agent（L2 独立判别器）      │
                    │  fresh 上下文 · 异角色 · 不参与生成    │
                    │  验收：是否卡内完成标准 · 是否自洽     │
                    └────────────────┬─────────────────┘
                                     ▼
                    ┌──────────────────────────────────┐
                    │  L3 逃逸监控                        │
                    │  · 校验器统计（L1 机器绿灯）          │
```

**递归深度上限 = 2**（orchestrator → domain agent）。不设第三层——若某批次复杂到需要孙子 agent，**该批次应拆为两个批次**，而非加深递归。

## 二、五项属性的实现机制

用户要求：可复用、可迁移、可沉淀、自进化、可生成。逐项落法：

### 2.1 可复用与可迁移

| 机制 | 做法 |
|---|---|
| **组织与任务解耦** | 本规格不含任何任务内容；任务以「批次契约」（§五）注入。换项目 → 换契约，组织不变 |
| **零硬编码路径** | 所有路径、并发上限、校验规则由 `docs/swarm/contracts/*.json` 承载（原 `config/swarm.json` 已并入契约文件，仓内不再单独存在） |
| **能力卡路径参数化** | 域 agent 收到的契约中明确指定「读哪张能力卡」，而非「用某个技能」——保证跨环境可执行 |
| **角色模板化** | domain agent 全部同一模板（读契约 → 读能力卡 → 产出 → 自检 → 返回清单），只有契约内容不同 |

### 2.2 可沉淀

| 沉淀物 | 位置 | 说明 |
|---|---|---|
| 产物文档 | `docs/requirements/NN-*.md` | 批次产出，git 追踪 |
| 批次契约 | `docs/swarm/contracts/*.json` | 每个批次的输入契约与验收标准，可回溯 |
| 内容指纹清单 | `docs/swarm/contracts/content-manifest.json` | 批次收口时冻结的 sha256，**冻结后不再更新**；内容变了却无人申报即判 FAIL |
| 修正台账 | `docs/swarm/contracts/applied-fixes.json` | 每条跨文档修正须附**可机械核对的证据**与新指纹；未申报的越权写入与不存在的修正一视同仁 |
| 校验器与自审 | `tools/verify_docs.py` / `tools/selftest_verify_docs.py` | 门禁与其负向测试——**绿灯只证明没报错，不证明检查在坏输入上会触发** |
| atomic note | 见 §七 | 蜂群内部消息的最小自包含单元 |

### 2.3 自进化

批次结束后执行**批次级复盘**，产出契约修订：

```
批次复盘（orchestrator 主持，goal-keeper 确认）
  ├ 输入：L1 校验结果 + L2 判别器报告 + 返工次数
  ├ 产出：契约修订（判定标准补强 / 新增必检项 / 收敛并合并）
  └ 生效：下一批次生效，不回溯改已完成批次
```

**关键纪律：自进化不回溯。** 已完成批次的产物不因后续修订而重写——否则每批次都可能有部分失效，结算成本无穷。自进化只改**判定标准**，不改历史产物；历史产物的修正走**显式挂账**（挂账清单累积到一定量级时统一处理）。

### 2.4 可生成

每次批次派生的 domain agent 组即为**临时组织**：成军 → 执行 → 产物落盘 → 解散。解散只回收 agent 实例，不回收产物与契约。产物与 agent 生命周期的分离即 L-REFORM 的开发侧兑现。

## 三、不可委托裁决（四类，判定门所在）

**这四类即使在无人托管授权下也保留判定门**——它们要么不可逆，要么定义产品含义，属 kernel §10 的 Non-delegable Core：

| # | 事项 | 理由 |
|---|---|---|
| 1 | **目标锚**（学什么、什么算学会） | 产品存在的理由，学习者本人不可被代理 |
| 2 | **License 与分发形态** | 法律承诺，不可逆 |
| 3 | **术语首选译法** | 是学习者的判断与偏好，不是分析可推导的结论 |
| 4 | **定义变更类决策** | 改变既有概念定义（如 B0 音频失效降级会把 B0 从零交互变为 B2 形态）——这不是技术选择，是产品定义变更 |

**除此以外的建模/分析/结构/文档决策，orchestrator 自主**，每次批次结束时以清单形式呈交 goal-keeper 批量过目，而非逐个打断。

## 四、记忆三分区与独立预算

| 分区 | 内容 | 预算 | 淘汰 |
|---|---|---|---|
| **Core** | 目标 + 不可变约束（goal-keeper 四类裁决、判定门红线、本仓 L0 账本优先原则） | 4k tokens | 不淘汰 |
| **Local** | 当前批次的契约、已完成批次摘要（不必带全文，带路径即可） | 8k tokens | 批次结束清空 |
| **Per-Child Queue** | 各域 agent 的待处理队列 | 2k tokens/agent | 最旧淘汰 |

**实际用法**：Local 分区只携带前 5 批的**路径与结论摘要**（约 20 行），不携带 1199 行全文。域 agent 需要细节时自己读文件——**这是 `docs/requirements/` 这套「只认产物不认对话」设计在上下文管理上的直接收益**。

## 五、批次契约（域 agent 的唯一输入）

每份契约固定六节：

```
1. 目标        —— 这一批要产出什么模型，为什么需要
2. 能力卡      —— 读哪张卡的哪个路径（绝对路径，跨环境可换）
3. 输入契约    —— 已完成产物里哪几份是本批的输入（给路径）
4. 文件所有权  —— 本批 agent 可写哪些文件（穷举，不含其他文件）
5. 验收标准    —— 卡内完成标准 + 本项目追加的可机械校验项
6. 返回契约    —— 必须返回什么：产物路径 + 跨文档修正建议清单 + 存疑项
```

**文件所有权是硬隔离**。域 agent 只能写第 4 节列出的文件；对其他文档的任何修正意见写进返回清单，**由 orchestrator 串行应用**。这条隔离是并发不冲突的唯一保证。

## 六、死法与对策

| # | 死法 | 机理 | 对策 |
|---|---|---|---|
| S1 | **共享文件并发写** | 多个 agent 同时改数据字典/BDD → 合并冲突 + 非确定性放大 | 文件所有权硬隔离；跨文档修正走返回清单，orchestrator 串行应用 |
| S2 | **生成与判定同体** | orchestrator 既派活又验收自己的产出 → 自我确认闭环 | L2 判别器必须 fresh 上下文，且**不参与任何生成** |
| S3 | **判断带宽超限** | 8 份大文档全需人判 → goal-keeper 放弃阅读，等于无人看 | L1 机器绿灯先过；只把非机械判断项上升 |
| S4 | **声明数字与实际不符** | 文档写「38 条关系」实际 21 条 → 规模守则自检失效 | 校验器交叉核对声明值与实际计数（**本项目已实际发生 2 次**） |
| S5 | **自进化回溯** | 修订契约后回改历史产物 → 每批次部分失效 | 禁止回溯；历史修正走挂账累积 |
| S6 | **并发数写死** | 换环境后并发上限不同 → 大量 agent 被拒 | 并发上限配置化，运行时读取 |
| S7 | **能力卡未加载即开工** | agent 凭通用知识产出 → 不符方法论 | 契约强制指定能力卡绝对路径；返回清单须声明已读 |
| S8 | **「完成」当「正确」** | 文档写完了就算交付 | L2 判别器按卡内完成标准逐条打勾，不看篇幅看标准 |

## 七、atomic note（蜂群内部消息最小单元）

```json
{
  "id": "note-b8-001",
  "issuer": "domain-agent-b",
  "batch": "batch-08-ui-dar",
  "timestamp": "2026-10-14T11:20:00Z",
  "tags": ["decision", "scope-change"],
  "summary": "B0 在 DAR 中缺少音频不可用时的显示规则，已列入返回清单",
  "evidence_ref": "docs/requirements/13-display-action-response.md#L42",
  "confidence": "medium"
}
```

**Interest-Aware 三态路由**：接收方已知 → DISCARD；需摘要 → COMPACT；需原文 → FULL。本项目场景中，域 agent 之间**不直接通信**，全部经 orchestrator——因为 4 个 agent 的产出彼此独立，直接通信的收益低于协调成本。

## 八、规模声明分层（诚实声明，不混称）

| 层 | 本次声明 |
|---|---|
| **组装层** | 首轮 4 个 domain agent 并行产出 8 份产物；第二轮 2 个修正 agent 并行返工。拓扑为星形（orchestrator 为唯一枢纽）；并发上限 4 |
| **治理层** | ✅ **已获实测证据**（非仅定义）：L2 判别器首轮判定 **FAIL**（8 份产物 4 达标 / 3 不达标 / 1 无法判定），抓出 12 处可定位缺陷；L1 在运行中当场拦下悬空 DD 引用（REF001）；**R1「越权写入由机器拦截」的声明经实测证伪后撤回**，改由内容指纹 + 修正台账取代。⚠️ **但门禁有已记录的天花板**：内容级检测判的是「变动是否申报」而非「谁改的」；声明计数仅覆盖 01/02/03；跨文档语义一致性零覆盖 |
| **端到端层** | ⚠️ **仍未验证**。「契约修订 → 生效 → 被证伪 → 再修订」这一圈**已完整走完一次**（R1 被实测打掉并由 R6 取代），故自进化闭环**存在但不等于有效**；而「产物全绿交付」这一层尚未达成——首轮判定为 FAIL |

**不做端到端声明**是硬纪律。组装层成功不等于治理层成立，治理层有证据也不等于端到端验证通过。

⚠️ **反例留档**：契约修订 R1 曾在 RETRO-01 中被写成「已修复」，而它守不住的正是本项目唯一的真实失败形态。**用一个能通过的门禁去声明它守不住的东西，比门禁缺失更危险**——它会关闭后续所有补门禁的动力。
