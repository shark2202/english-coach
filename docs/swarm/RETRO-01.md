# L3 逃逸监控与批次复盘 v0.1

## 一、L3 逃逸事件登记

**逃逸定义**：门禁应当拦下、但产出仍以某种形式进入仓库的现象。L3 度量的是**缺陷「发现层 − 发生层」**——逃逸距离变长 = 门禁 Goodhart 化。

### 1.1 本轮登记的 4 起事件

| # | 事件 | 发生者 | 性质 | 处置 | 结果 |
|---|---|---|---|---|---|
| **E1** | 批次 8 agent 越权修改 `README.md`（README 不在其 owns 清单） | agent-B | **越权写入** | orchestrator 串行复核后保留其内容 | ✅ 内容正确 |
| **E2** | 批次 7 agent 越权修改 `README.md` | agent-D | **越权写入** | 同上 | ✅ 内容正确 |
| **E3** | 某 agent 修改 `docs/swarm/ORG-SPEC.md` 路径表述 | 未确认（批次 7/8/9 之一） | **越权写入 + 修正 orchestrator 的错误** | 核实后保留 | ✅ **它修的是我的错**：我写「`config/swarm.json` 承载」，实际文件建在 `docs/swarm/contracts/` |
| **E4** | 某 agent 新建 `AGENTS.md`（133 行工程规范） | 未确认 | **越权创建** | 核实内容扎实后保留 | ✅ 与蜂群设计一致 |

**另有一起被门禁成功拦下的**：

| 事件 | 拦截者 | 结果 |
|---|---|---|
| agent 在第二份文档写出前先引用了它（`10-*.md` 链接 `11-system-flow.md`，`14-*.md` 链接 `15-*.md`） | **L1 校验器 LK001** | 飞行中 FAIL 4 → 收工后自然清零 |

### 1.2 本轮逃逸事件的性质判定

**4 起越权写入，全部内容正确。这不是好消息，是坏消息。**

理由：门禁**没有拦住任何一起**。它们能进入仓库，靠的不是校验器，而是我事后人工复核。**如果我复核时恰好忙碌或疏漏，它们就会以未经授权的状态固化。**

**更值得注意的是 E3/E4 的组合**：agent 修正了 orchestrator 的错误、创建了缺失的入口文件——**行为上完全正确，但恰恰因为「明显正确」而最难被拒绝**。这比明显的越权更危险：它让人倾向于接受。

### 1.3 逃逸距离统计

| 指标 | 值 |
|---|---|
| 本轮产生批次 | 4（批次 6/7/8/9） |
| 被 L1 拦截 | 1（悬空链接） |
| 被 L2 拦截 | 待判别器运行 |
| 被 L3 事后捕获 | 4（越权写入） |
| **逃逸距离（发生层 − 发现层）** | **4 —— 全部由事后捕获，非门禁拦截** |

**判定**：门禁强度不足。L1 覆盖了计数、链接、frontmatter、陈旧表述，**但没有任何一项检查「写入的文件是否在契约 owns 清单内」**——这是最该有的检查，因为越权写入是本轮唯一的失败模式。

### 5.2 撤回 R1：越权写入并未被机器拦截

**这是本次复盘最重要的结论，且结论对我自己不利。**

契约修订 R1 写的是：*「校验器读取契约 owns 清单核对，越权写入由机器拦截，**不再依赖 orchestrator 事后复核**」*，RETRO-01 §三 把它列为「下一批必须验证的第一件事」。

**验证结果：这句话不成立，现予撤回。**

判别器的实测方式：改掉 `12-user-interface-flow.md` 的内容而**不动** `batch:` 字段 → `OWN001`/`OWN002` 全绿。而 RETRO-01 §1.1 登记的 4 起越权**恰恰就是这种形态**——agent 改了别人的文件内容，`batch:` 声明仍指向原属主。

| R1 声称能拦 | 实际能否拦 |
|---|---|
| frontmatter 声明与契约归属不符 | ✅ 能 |
| 契约未授权的新建文件 | ✅ 能 |
| **改了不属于自己的文件内容** | ❌ **不能** |

**用一个能通过的门禁去声明它守不住的东西，比门禁缺失更危险**——它会关闭后续所有补门禁的动力（这正是死法 S8 的镜像形态）。若照原样宣布治理层闭合，R1 会以「已修复」的状态固化为一段假账。

### 5.3 门禁重做（契约修订 R6）

新增 `MAN001` 内容指纹检查，其数据源为两份台账：

| 文件 | 作用 |
|---|---|
| `docs/swarm/contracts/content-manifest.json` | 冻结 21 份产物的 sha256。**冻结后不再更新** |
| `docs/swarm/contracts/applied-fixes.json` | 每次合法修正须申报 `new_sha256`，并附 `evidence`（可机械核对的内容证据） |

判定规则：文件内容的 sha256 **要么**等于清单冻结值（未动），**要么**等于台账中某条已申报的新指纹。**其余一律 FAIL。**

这直接堵住 R1 的漏洞：agent 改了别人的文件 → 内容指纹失配且无人申报 → L1 判 FAIL。

**R5（校验器自审）同步落地为 `tools/selftest_verify_docs.py`**，30 项用例覆盖每条检查的正例与负例。它在编写当场就抓出两个真实问题：4 个正例因路径解析错误被误判，以及若干负例「因为错误的原因而通过」——即目标文件根本不存在，FIX001 仍然报了同一个码。**这说明门禁的负向测试本身就是必要的：绿灯只证明没报错，不证明检查在坏输入上真的触发。**
