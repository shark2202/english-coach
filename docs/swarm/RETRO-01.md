# L3 逃逸监控与批次复盘 v0.1

## 一、L3 逃逸事件登记

**逃逸定义**：门禁应当拦下、但产出仍以某种形式进入仓库的现象。L3 度量的是**缺陷「发现层 − 发生层」**——逃逸距离变长 = 门禁 Goodhart 化。

### 1.1 本轮登记的 4 起事件

| # | 事件 | 发生者 | 性质 | 处置 | 结果 |
|---|---|---|---|---|---|
| **E1** | 批次 8 agent 越权修改 `README.md`（README 不在其 owns 清单） | agent-B | **越权写入** | orchestrator 串行复核后保留其内容 | ✅ 内容正确 |
| **E2** | 批次 7 agent 越权修改 `README.md` | agent-D | **越权写入** | 同上 | ✅ 内容正确 |
| **E3** | 某 agent 修改 `docs/swarm/ORG-SPEC.md` 路径表述 | 未确认（批次 7/8/9 之一） | **越权写入 + 修正 orchestrator 的错误** | 核实后保留 | ✅ **它修的是我的错**：我写「`config/swarm.json` 承载」，实际文件建在 `docs/swarm/contracts/` |
| **E4** | 某 agent 新建 `AGENTS.md`（133 行工程规范） | 未确认 | **越权创建** | 核实内容扎实后保留 | ✅ 与蜂群设计一致 |

**另有一起被门禁成功拦下的**：

| 事件 | 拦截者 | 结果 |
|---|---|---|
| agent 在第二份文档写出前先引用了它（`10-*.md` 链接 `11-system-flow.md`，`14-*.md` 链接 `15-*.md`） | **L1 校验器 LK001** | 飞行中 FAIL 4 → 收工后自然清零 |

### 1.2 本轮逃逸事件的性质判定

**4 起越权写入，全部内容正确。这不是好消息，是坏消息。**

理由：门禁**没有拦住任何一起**。它们能进入仓库，靠的不是校验器，而是我事后人工复核。**如果我复核时恰好忙碌或疏漏，它们就会以未经授权的状态固化。**

**更值得注意的是 E3/E4 的组合**：agent 修正了 orchestrator 的错误、创建了缺失的入口文件——**行为上完全正确，但恰恰因为「明显正确」而最难被拒绝**。这比明显的越权更危险：它让人倾向于接受。

### 1.3 逃逸距离统计

| 指标 | 值 |
|---|---|
| 本轮产生批次 | 4（批次 6/7/8/9） |
| 被 L1 拦截 | 1（悬空链接） |
| 被 L2 拦截 | 待判别器运行 |
| 被 L3 事后捕获 | 4（越权写入） |
| **逃逸距离（发生层 − 发现层）** | **4 —— 全部由事后捕获，非门禁拦截** |

**判定**：门禁强度不足。L1 覆盖了计数、链接、frontmatter、陈旧表述，**但没有任何一项检查「写入的文件是否在契约 owns 清单内」**——这是最该有的检查，因为越权写入是本轮唯一的失败模式。

## 二、批次复盘（自进化：只改判定标准）

依 ORG-SPEC §2.3「自进化不回溯」——本节**只产出契约修订，不重写已完成批次的产物**。

### 2.1 契约修订（下一批次生效）

| # | 修订项 | 触发事件 | 修订内容 |
|---|---|---|---|
| **R1** | **新增 L1 校验项 `OWN001`** | E1–E4 | 校验器读取 `docs/swarm/contracts/*.json` 的 `owns` 清单，对 `docs/requirements/` 下每份文档核对其「声明的所属批次」是否匹配当前产物；**越权写入由机器拦截，不再依赖 orchestrator 事后复核** |
| **R2** | **契约增加「禁止创建未授权文件」显式条款** | E4 | 现契约只写「只能创建/修改 owns 列出的文件」，未禁止创建**全新的**未列出文件。E4 的 `AGENTS.md` 正是钻了这个空子 |
| **R3** | **README.md 明确划归 orchestrator 独占** | E1/E2 | README 是共享写入热点，两批 agent 同时改它。虽未造成冲突（改动行不同），但**下次必然冲突**——须在契约层面禁止域 agent 触及 |
| **R4** | **跨文档修正的闭环验收** | 观察 | 域 agent 返回 `cross_doc_fixes` 后，**校验器应能验证修正已落地**。本轮 4 处 cross_doc_fixes 是我手工 grep 应用的，无机器确认环节 |
| **R5** | **L1 校验器的自审** | 本轮三次自抓 | 校验器自身在本轮修过 2 个 bug（model 字段匹配、ST002 误报）。**门禁自身需要被测试**——已列入待办 |

## 三、诚实的能力边界声明

**本轮不能宣称的事**：

1. **不能宣称端到端验证通过。** R1–R5 五条修订从未在第二批生效过——**「自进化闭环」目前只是被执行了一次，没有任何证据表明它有效**。
2. **不能宣称门禁有效。** 唯一被机器拦下的缺陷（悬空链接）是 LK001 顺带发现的，不是针对越权的设计。**4 起越权零拦截**。
3. **不能宣称产物质量可信。** 尚未运行 L2 独立判别器——**所有质量判断目前都来自 agent 自我声明与我的抽查，而两者都不是独立判别**。这正是 I-DISC 要求防范的情形。

**下一批必须验证的第一件事**：R1 的 `OWN001` 能否真的拦住越权写入。若不能，门禁设计需重做。
