## 一、错题——自我修正闭环（本项目最关键的一张图）

```
                    ┌──────────────────────────────┐
                    │                              │
                    ▼                              │
    ┌───────────────────────┐                      │ 同错二犯
    │      (未修复)          │──同类错误再犯──────────┤
    └───────────┬───────────┘                      │
                │ 首次入本                          │
                ▼                                  │
    ┌───────────────────────┐                      │
    │      (待验证)          │──验证未通过──────────►│
    └───────────┬───────────┘                      │
                │ 验证通过                          │
                ▼                                  │
    ┌───────────────────────┐                      │
    │      (已修复)          │──持续观察─┐          │
    └───────────┬───────────┘           │          │
                ▲                       │          │
                │ 再次验证通过           │          │
                │                       ▼          │
    ┌───────────┴───────┐       ┌──────────────────────────────┐
    │      (复发)         │───────│          (复发)              │
    └───────────────────┘       └──────────────────────────────┘
```

**这张图要回答的唯一问题**：*「学会了」这件事，在系统里是什么形状？*

答案是：**不是一个状态，是一个反复重新达成的状态**。`(已修复)` 永远待在一根回退线上——因为 org-design §6.1 把「错题修复率（同错二犯率）」列为**核心指标**，而任何不允许二犯的状态机，都会让这个指标恒为 100%，从而**作废整个质量度量体系**。

**卡内 B 段警告的实证**：「轻率标无效——标『无』开发会真的阻止它，终态复活常被误杀」。本图的三条 `↩`（未修复↺待验证、已修复↺复发、复发↺已修复）正是被误杀就会致命的三处。

## 二、维度掌握度——升降与衰减

```
                  连续达标上移（样本≥5 且锚位连续2次稳定）
        ┌──────────────────────────────────────────────┐
        │                                              ▼
   ╭────────────╮ 连续达标上移                 ╭────────────╮
   │    (生)     │────────────────────────────►│  (自动化)   │
   ╰────────────╯                             ╰────────────╯
        │      ▲                                   │     ▲
        │      │ 跌破下移                           │     │ 跌破下移
        │      │                              跌破下移   │
        │      │                                   │     │
        ▼      │                                   ▼     │
   ┌───────────────────────┐ 连续达标上移    ┌────────────┐
   │       (半熟)           │───────────────►│            │
   └───────────────────────┘                └────────────┘
        ▲                                             
        └──────────── 跌破下移 ──────────────────────────┘
```

**关键读法**：图中两条 `跌破下移` 虚线（从半熟到生、从自动化到半熟）是**能力会退步**的机制化表达。若把它们删掉——只在向上箭头流动——模型就退化成 v0.1 的「越用越强」，而这在现实中不成立：长时间不练，`(自动化)` 会退回 `(半熟)`，进而退回 `(生)`。

**被刻意禁止的捷径**：(生) →(自动化) 无箭头。卡内 E6「能否跳过某状态」的答案在这里是**不能**——跳过会使掌握度曲线失真，SM5 的轨迹斜率不可解释，而 SM6（判定难度分布）正是靠这条曲线的可信度来证伪 SM1 的。

## 三、练习项——锁、心跳与接管

```
   ◎(待补切)
      │ 补切完成（材料+预嵌细则齐备）
      ▼
  ┌──────────┐
  │  (可取)   │◄──────────────┐
  └────┬─────┘               │
       │ 取用并加锁           │ 心跳超时释放  ↩①
       ▼                     │  ┌────────────┐
  ┌──────────┐               │  │  (锁定)     │
  │  (锁定)   │───────────────┘  └─────┬──────┘
  └────┬─────┘                         │ 消费完成
       │                               ▼
       │                        ┌──────────┐
       │ 水位回收 ↩②             │ (已消费)  │
       └────────────────────────►│          │
                                └────┬─────┘
                                     │ 判定降级复查 ↩③
                                     ▼
                                ┌──────────┐
                                │  (作废)   │◉
                                └──────────┘

   (待补切) ──材料作废──► (作废)
   (可取)   ──材料作废──► (作废)
```

**这张图承载死法 A3 的全部防线**：

| 编号 | 回退 | 失去它会怎样 |
|---|---|---|
| ↩① | 锁定 → 可取 | 设备崩溃/被杀 → 该项**永久**被锁死，队列逐项耗尽 → App 空转 |
| ↩② | 可取 → 待补切 | 队列无法重整，水位线策略失效 |
| ↩③ | 已消费 → 作废 | **本轮新发现**：T0/T1 判定质量塌陷时无重练路径，死法 A9 只能被动承受 |

`↩③` 是上一轮设计里完全不存在的转变。它的来源是 BOM v0.3 新登记的死法 **A9（离线判定质量塌陷）**——既然承认降级判定可能不可信，就必须有一条「作废重做」的路，否则降级只会被记录而不会被纠正。

## 四、能力画像与同步游标——两个退居后台的状态机

### 4.1 能力画像（新鲜度心跳）

```
   ◎(现行) ◄────── 新判定记录到达 ──────┬────── (陈旧)
      │                                  │        ▲
      │ 超 14 天无判定                    │ 超 14 天无判定
      ▼                                  │        │
   ┌──────────┐                          └───►─────┘
   │  (陈旧)   │  ── 陈旧期间材料编排降级为通用兜底包（不按过期画像编排）
   └────┬─────┘
        │ 能力重估 / 策略重定
        ▼
   ┌──────────┐
   │ (已封存)  │◉   ← 全部历史画像保留，为 SM5 的变化轨迹提供数据
   └──────────┘
```

`现行 ⇄ 陈旧` 是一个**自持循环**：它不靠练习推动，而靠「多久没练」推动。这正是 BOM v0.3 的 G4——**画像新鲜度的对手不是判断错误，是时间本身**。

### 4.2 同步游标（同步三态 → 四态）

```
   ◎(单机) ──用户开启同步──► ┌──────────┐
     ▲   ▲                   │ (同步中)  │
     │   │                   └────┬─────┘
     │   │ 用户关闭同步            │ 同步完成
     │   │                   ┌────▼─────┐
     │   └───────────────────┤ (已同步)  │◄──── 下次同步开始 ────┐
     │                       └────┬─────┘                      │
     │                            │ 下次同步失败                │
     │                            ▼                             │
     │                       ┌──────────┐      自动重试 ─────────┤
     └───────────────────────┤(同步失败) │                      │
        用户关闭同步           └──────────┘────────┘             │
                                                        (同步中) ┘
```

**⚠️ 这张图改写了既有设计**：**写本图时**，`app-design.md` §九 A10 的对策写的是「同步状态显式**三态**」。但同步失败时，三态中的任何一态都是**撒谎**：

- 归「同步中」→ 界面永远转圈，学习者以为在同步，其实早已失败；
- 归「单机」→ 失败被掩盖，账本已陈旧却显示「单机模式，功能完整」。

**A10 的对策本质是「不假装新鲜」，而把失败塞进三态恰恰是在假装。** 故本图新增第四态 `同步失败`，并要求批次 4 的决策表补齐「同步失败 → 界面如何呈现」的分支。

⚠️ **现状对齐（2026-10-14）**：`app-design.md` §九 A10 的三态旧措辞**已由编排者改为四态**，与本图新增的第四态一致；`03-data-dictionary.md` v0.2 的 DD703 亦已按同一理由扩为四态（其 §三 挂账 2 已登记，原三态的表述留在该挂账内作为历史）。**本图的论证不因上游改写而失效——它论证的正是「为什么必须扩为四态」。**

## 五、跨对象合并视图——一轮完整判定的链路

> 本节不在卡内要求内，是本轮为验证「三张图合起来是否自洽」而做的合并核对。

```
   材料(入库) ──► 练习项(可取) ──► 练习项(锁定) ──► 交互轮次落盘
                      │                                  │  ← append-only，不变
                      │                                  ▼
                      │                            判定(待判定)
                      │                                  │
                      │                      ┌───────────┼───────────┐
                      │                      ▼           ▼           ▼
                      │                 判定正确    判定不自然   低置信
                      │                      │           │           │
                      │                      │           │      待复核
                      │                      │           │           │
                      │                      │           │      T2补判 ↩④
                      │                      │           │           │
                      │                      ▼           ▼           ▼
                      │                   ┌────────────────────────────┐
                      │                   │  错题(未修复) ──首次入本──►   │
                      │                   └────────────────────────────┘
                      │                              │
                      │                        验证通过 / 未通过
                      │                              ▼
                      │                      错题(待验证) ──► (已修复)
                      │                                              │
                      │                                          同错二犯 ↩⑤
                      │                                              ▼
                      │                                        错题(复发)
                      │
                      └──► 判定结果 ──► 维度掌握度 升降 ──► 能力画像刷新
                                          │                      │
                                          └──────────────────────┘
                                                 画像持续新鲜
```

**合并视图暴露的一处结构问题**：`(材料)`、`(练习项)`、`(交互轮次)` 三者都在链路上，但**它们的触发事件来源不同**——材料由标注流程驱动、练习项由队列调度驱动、轮次由用户行为驱动。三条驱动线在状态表里是独立的八张表，合并后才发现：**没有任何一张表说明「材料被淘汰时，正在锁定它的练习项怎么办」**。

**已补规则**（见状态表 §一、§五）：材料 → 作废 触发练习项 → 作废。**这是本轮通过合并视图才发现的跨表缺口**——单看任一张表都不觉得有问题。
