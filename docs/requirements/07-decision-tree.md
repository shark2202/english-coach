## 一、冷启动自举——L-RESUME 的执行算法

> 来源：org-design §三「会话自举协议」+ app-design §4.2「冷启动自举 = 读缓存 + journal 尾行校验 → 直接呈现续学点」

```
◎ 冷启动
  │
  ◇ 设备有可用缓存（learner-state + journal 尾行）？
  │
  ├── 否 ──► ◇ 账本目录可读？
  │          ├── 否 ──────────────────► ▭【首次运行】引导锁定目标锚（T1 触点）后建队列
  │          └── 是 ──► ◇ 能力画像存在且现行？
  │                        ├── 否 ────► ▭【画像缺失】按目标锚难度带补切队列 → 首练
  │                        └── 是 ────┐
  │                                   │
  └── 是 ──► ◇ 缓存尾部与 journal 尾行一致？│
              ├── 否 ──► ◇ 以 journal 尾行为准重建缓存 ──┐│
              └── 是 ────────────────────────────────┐││
                                                      ▼▼▼
                                              ◇ 存在续学点？（journal 尾行可定位轮次）
                                                      │
                     ┌────────────────────────────────┴───────────────────────────┐
                     │ 否                                                          │ 是
                     ▼                                                            ▼
              ◇ 目标锚已锁定？                                          ▭【续学】呈现续学点
              ├── 否 ─► ▭【引导】锁定目标锚（T1）                                并标注来源设备与时刻
              └── 是 ─► ▭【首练】按档位取队列首项 ────────────────────────────► 唤起条
```

**校验**：根到每个叶子均到达 `▭`，无悬空分支；`▭` 无出线 ✅

**卡内 E5「简化决策树」检查**：
- 「缓存尾部与 journal 尾行不一致 → 重建缓存 → 续学点」这条路径上，**判断没有反复出现在多处**，无需上提 ✅
- 「以 journal 尾行为准」是正确的默认值方向：**账本（append-only journal）是唯一事实源，缓存是派生物**（L-NOLOSS / 账本优先）。若方向反了——信缓存而废 journal——会直接击穿 L-RESUME。**这棵树把「谁优先」写进了判断顺序本身**，是它比文档段落更可靠的地方。

**⚠️ 与 DD104 的接口**：本树「【首次运行】」分支产生的是**无轮次会话**（B0 档）。数据字典 DD104 允许悬空，本树确认了该场景真实存在，**不是建模冗余**。

## 二、判定执行与 T2 补判回环——死法 A9 的执行闭环

> 与 `06-decision-table.md` DT-1 配套：DT-1 定「用哪一级」，本树定「判完之后怎么走」。

```
◎ 交互轮次落盘（append journal）
  │
  ◇ 判定对象 = 理解率？
  ├── 是 ──► ◇ 本窗口样本量达标？
  │            ├── 否 ──► ▭【跳过】仅记数据点，不产判定
  │            └── 是 ──► ▭【统计】滚动正确率入画像 → 触发 DT-2 难度锚动作
  │
  └── 否 ──► ◇ DT-1 选出判定级别（T0 / T1 / T2）
               │
               ▼ 执行判定
               ◇ 置信度 ≥ 0.70？
               │
      ┌────────┴─────────┐
      │ 是                │ 否
      ▼                  ▼
  ▭【落盘】判定结果    ▭【待复核】标记并入补判队列（DD203 = 待复核）
  （带级别标记 DD104）      │
                            ▼
                    ◇ 联网 且 同步状态 = 已同步？
                    ├── 否 ────────────────────────► ▭【保持待复核】不阻断训练
                    │                                  计入降级统计
                    └── 是 ─► ◇ 执行 T2 补判
                                 │
                                 ◇ 补判置信 ≥ 0.70？
                                 ├── 是 ─► ▭【覆盖】T2 结果覆盖原判，入错题本
                                 └── 否 ─► ▭【挂起】保留待复核
                                            │
                                            └─► ↩⟳3 回到「执行 T2 补判」
                                                （限 3 次，达上限则永久挂起
                                                  并计入 SM5 降级斜率）
```

**校验**：无死角 ✅；回环**已限次 3 次**，不构成无限循环 ✅

**限次的理由**：状态表 §二允许「判定正确 → 待复核（事后置信下调）」的无休止回流。决策树层面的限次是**工程上必需的兜底**——一个持续失败的补判若无限重试，会在每次会话启动时反复消耗 API 配额并延迟开练。**3 次是本轮设定的初值，未经实测**，应作为配置项而非硬编码。

**双模原则在此兑现**：「联网 且 同步已同步」为否时，判定**不阻断训练**，直接落到「保持待复核」——同步失效不降级单机功能一分（app-design §二）。

## 三、队列取用与降级——死法 A3 的最后防线

```
◎ 唤起（学习者给定档位 B0/B2/B5/B15）
  │
  ◇ 该档位队列水位 ≥ 2？
  ├── 是 ──► ◇ 取队首项并加锁 ──► ▭【开练】正常路径
  └── 否 ──► ◇ 该档位队列非空（≥1）？
              ├── 是 ─► ▭【降级开练】取该项（水位不足）
              │        + 登记补切任务（后台，永不阻塞唤起）
              └── 否 ─► ◇ 本地兜底包存在？
                        ├── 是 ─► ▭【兜底开练】取兜底包 + 登记补切
                        └── 否 ─► ◇ 网络可用？
                                  ├── 否 ──► ▭【空转提示】「队列空且离线」
                                  │            + 显示同步状态 + 登记补切
                                  │            （不重试，等下次唤起）
                                  └── 是 ──► ◇ 同步状态 = 已同步？
                                                ├── 否 ─► ▭【不可生成】显示陈旧读提示
                                                │        标注「账本同步至 T（来源 X）」
                                                │        待复核 → 上一级「队列非空？」
                                                └── 是 ─► ▭【可补切】同步完成后即时补切
```

**校验**：无死角 ✅；**无无限回环** ✅（「不可生成」分支的「待复核 → 上一级」是单次回跳，不构成循环——回跳后仍为空则落入空转提示）

**卡内 E5 的可用性警告检查**：卡内称「用户必须做超过 10 个判断才能得到结果，几乎肯定放弃」。本树中**学习者只需做一个判断（选档位）**，其余 5 个判断全在系统内自动完成——**这正是三触点极简策略的实现形态**。若把队列水位、兜底包、同步状态这些判断暴露给学习者，触点原则立即崩塌。

**兜底包的双重价值**：它既是死法 A3 的防线（队列空不空转），也是**画像陈旧时的降级载体**——当能力画像转为陈旧（G4 命中），编排不再按过期画像进行，而是回落到通用兜底包。**同一机制，两处用途。**

## 四、同步失败处理——状态表新增第四态的落地

> 状态表 §八发现「同步失败」必须独立成态。本树定义它的处理分支，全部遵守**双模原则：同步失效不降级单机功能一分**。

```
◎ 检测到同步失败
  │
  ◇ 失败原因可判定？
  │
  ├── 是：本地存储不足 ──────────► ▭【暂停同步】提示清理空间
  │                                   账本仍可读写，单机功能完整
  │
  ├── 是：云服务未登录 ──────────► ▭【降级单机】提示登录
  │                                   ⚠️ 明确告知「已转入单机模式」而非静默降级
  │
  ├── 是：存在未解冲突 ──────────► ▭【挂起】展示冲突项供人工裁决
  │                                   journal 天然可并集；chunk-ledger 冲突须人工
  │
  └── 否 ─────────────────────────► ▭【标记】标注「同步失败 + 最后同步时刻」
                                       继续单机运行，下轮自动重试
```

**校验**：四个分支全部直达 `▭`，无死角 ✅

**本树是状态表 §八 结论的直接兑现**。若沿用原三态，「云服务未登录」这一分支**根本不会被触发**——系统会以为自己在「同步中」，无限等待，而学习者看到的是一个永远转圈的界面。**那正是 A10 陈旧读幻觉的完整形态：不撒谎的代价是把失败显式化，而失败一显式化就必须有处理分支。**

**与界面模型（DAR，批次 8）的接口**：四个 `▭` 各自的界面呈现（文案、是否阻断、是否显示最后同步时刻）待 DAR 定义。

## 六、挂账与下游接口

1. **§二 的 T2 补判限次 3 次**：初值未经实测，应作为可换配置（对齐 app-design §二「调度算法都是可换配置」的惯例）。
2. **§三 的「登记补切任务」**：补切由语料局在后台执行，其失败路径属系统流程（批次 9），本树只覆盖唤起侧的判断。
3. **§四 的「未解冲突」人工裁决**：chunk-ledger 的行级 LWW 策略（app-design §八）是否足以自动消解，取决于是否允许「静默丢弃一方」。⚠️ **这与「宁可重复，不可丢失」的原则冲突**，已登记为需批次 5（接口表）与批次 9（系统流程）共同裁决。
4. **§一 的「可用缓存」判定**：缓存有效性尚无独立状态位承载（数据字典未定义），实现时需补一个派生标记。
