# 系统流程 v0.1

> **一句话**：处理流程说「学习者做什么」，用例说「承诺什么」，本图说「**用户按下那个按钮之后，机器自己会做什么、按什么顺序做、每一步坏了怎么办**」——本图是实现者唯一的执行规格，也是 AC2/AC5/AC11 三条可测性要求的流程侧依据。

---

## 零、口径与边界（四条纪律，先说清本图不做什么）

### 0.1 不描述用户活动（卡内 B 段首条）

学习者**不设泳道**。学习者的每一次动作在本图中只能以两种形态出现：

| 形态 | 何时用 | 例 |
|---|---|---|
| **事件** | 用户的一次触发动作 | 「唤起」「轮次提交作答」「周度触点确认」「难度反馈」 |
| **外部实体的输入流** | 持续供给的数据 | 作答文本、语音 |

⚠️ **一个高频易错点**：把「学习者阅读材料」「学习者选择档位」写成系统流程里的步骤。卡内警告「系统反应和用户操作混淆（把系统当成处理流程的人，应把系统行动移到系统流程）」。本图的做法是：用户操作一律以事件出现在**触发它的那条系统泳道上**（卡内 E1），流程里只留系统自己的动作。学习者动作的完整表达在 [处理流程](16-process-flow.md) 与 [用例](17-use-case.md)。

### 0.2 不重画决策逻辑（卡内 B 段）

分支的**枚举**唯一权威在 [决策树](07-decision-tree.md)（4 棵）与决策表。本图只写「分支被选中之后，系统按什么顺序执行哪几步、每步失败怎么办」。

**引用格式**：`⟨分支依据：07-decision-tree §二 · T2 补判回环⟩`。凡出现此格式处，本图**有意不重复分支内容**——重复一遍就会产生第二个权威，而两份不同步的权威比没有权威更危险。

### 0.3 泳道来源（卡内 E5：泳道上使用的系统应出现在生态系统图上）

| 泳道 | 层 | 生态图回指 |
|---|---|---|
| 壳层（Lynx · VueLynx） | L3 | 组 1 · L3 |
| 教练核心 coach_core（纯 TS） | L1 | 组 1 · L1 |
| 账本契约（md / jsonl 文件） | L0 | 组 1 · L0 |
| 教练官（提示词） | L2 | 组 1 · L2 四角色 |
| 选材官（提示词） | L2 | 组 1 · L2 |
| 陪练官（提示词） | L2 | 组 1 · L2 |
| 判读官（提示词） | L2 | 组 1 · L2 |
| 记忆官（**调度算法在 L1，不调 LLM**） | L1 + L2 | 组 1 · L1（app-design §二 关键判决） |
| 平台能力（TTS / 后台播放 / 文件 I/O） | L4 | 组 3 |
| 同步通道 ⊘（iCloud Drive 等） | 组 4 | 组 4（可选叠加层） |
| 开发/运维侧（编辑器 / CLI 壳 / 补切脚本） | 组 5 | 组 5 |

**11 条泳道全部可回指，无一条是用户角色** ✅

### 0.4 范围外的上下文步骤（卡内 B 段「漏掉范围外上下文步骤」）

卡内要求：应包含范围外的**前后**步骤以界定边界。本图明确标出两处：

- **前置（范围外）**：`1.0 上一次会话被中断（未走收尾）` —— 设备被杀、App 被系统回收、来电中断。本图的 `1.2 冷启动自举` 必须能在这个状态下正确接管，否则边界外的故障会击穿范围内的续学承诺（AC2）。
- **后置（范围外）**：`1.9 之后：学习者可能立刻离开、锁屏、换设备` —— 系统不得在用户离开后「后台偷偷续跑」（app-design §4.2 明确禁止），`1.8 会话收尾` 之后不再有系统动作。

## 一、事件目录（卡内 E5：事件须标注响应时间 / 频率要求）

卡内原文：「实时与嵌入式系统必须在系统流程中标注事件，并描述对事件的响应时间要求（如下一步之前的最大等待时间）与预期事件数量，让工程师了解性能需求。」本项目非实时系统，但**取件、落盘、补切、同步四条链都有硬时限**，故全量标注。

**响应时间两栏的含义**：`上限` = 该事件到下一步骤完成的最大允许等待；`内部分目标` = 实现期用于分解的内部指标（比 AC 宽严不同，已注明来源）。

| # | 事件 | 类型 | 触发方 | 响应上限 | 内部分目标 | 预期频率（拟案） | 证据 |
|---|---|---|---|---|---|---|---|
| **E-1** | 唤起 | 用户触发 | 壳层 / 唤起入口 | **< 2 秒**至首个练习可呈现 | 账本读路径 **≤ 300 ms** | 5–10 次/日 | AC1（上界已冻结）；内部分目标为拟案 |
| **E-2** | 轮次提交 | 用户触发 | 壳层 | 落盘完成后方可返回 UI，**≤ 100 ms** | 同左 | 3–8 次/会话 | app-design §4.2 微落盘 |
| **E-3** | 学习者离开（进入后台） | 外部 | 平台 | 当轮完成即安全停机，**不做后台续跑** | — | 随机 | app-design §4.2 |
| **E-4** | 消费锁心跳 | 时间间隔 | 教练核心 | 每轮刷新 1 次；**TTL 约 10 分钟** | — | 每轮 1 次 | 04-state-table §一 复活路径① |

| **E-7** | 网络可用性变化 | 外部 | 平台 | 变化即评估，**不打断当前轮** | — | 随机 | — |
| **E-8** | 账本目录变更 | 外部 | 同步通道 / 文件通知 | **Handoff 即时；仅文件同步 ≤ 1 分钟** | — | 每轮落盘 1 次 | AC9（上界已冻结） |

## 二、L1 系统流程：一次微会话的端到端自动化

> 步骤命名格式：`<系统>+<动作>+<对象>`（卡内 E4）。用泳道时系统名可省，在泳道上；跨系统读写时指定目标系统为 `<行动>+<对象>+<目标系统>`。
> 编号与特性树的对应：L1 的 9 步对应特性树的会话主链特性（批次 8/9 交叉校验点）。

## 三、L2 · 1.2 冷启动自举

> **与决策树的关系**：[07-decision-tree](07-decision-tree.md) §一 给的是判断分支（缓存有无 / 是否一致 / 有无续学点 / 目标锚是否锁定）。本节给的是**执行顺序与失败补偿**——决策树回答「走哪条路」，本节回答「每条路上机器先做什么、坏了怎么办」。两者重叠处不重复表述。

```
1.2.1  壳层      接收 E-1 唤起事件，解析唤起意图（默认档 / 指定档 / 只要听 / 难度反馈 / 停）
1.2.2  教练核心   读取 learner-state 快照 ▸ <学习者.目标锚> <学习者.难度档> <语境域矩阵>
        │
        ├─ 读失败 ─► 1.2.7（账本不可读分支）
        ▼
1.2.3  教练核心   读取 journal 尾行 ▸ <交互轮次.轮次 ID> <设备 ID> <轮次序号>
1.2.4  教练核心   比对缓存尾行与 journal 尾行是否一致
        │ 一致 ─────────────────────────────┐
        │ 不一致 ─► 1.2.5 重建              │
        ▼                                     ▼
1.2.5  教练核心   以 journal 为准重建 learner-state 缓存（journal 是唯一事实源，L-NOLOSS）
        │  重建失败 ─► 保留旧缓存 + 标记「缓存不可信」→ 只读呈现，仍给续学点
        ▼
1.2.6  教练核心   定位续学点 ⟨无续学点 → 07-DT §一「首练 / 引导 / 首次运行」分支⟩
1.2.7  壳层      呈现续学点 + 来源设备 + 同步至时刻 ⟨账本不可读 → 明确错误，不假装⟩
```

**为什么「以 journal 为准」的方向不能反**：若信缓存而废 journal，一次未落盘的崩溃或一次半写文件就会被缓存掩盖，学习者会回到一个**不存在的续学点**——这直接击穿 AC2（损失 ≤1 轮）。决策树 §一 把这个方向写进了判断顺序，本节把它写进了执行顺序，两者一致。

1.5.8  教练核心   扫描 ▸ 待复核 且 判定级别 ≠ T2 的判定行
        │ 无 / 网络不可 / 同步状态 ≠ 已同步 ─► 保持待复核（不阻断训练，双模原则）

        │ 是 → 覆盖原判（覆盖不累积）+ 更新错题本 ▸ error-book

⚠️ **`1.5.6` 的 I-DISC 校验失败怎么办**（既有文档未覆盖，本图新增）：若重放出的判读请求体含有陪练官上下文（接口表 IF-1 禁止清单任一项），**判读结果作废**，重试 1 次；仍失败则该轮判定标为降级并入待复核，同时报警。理由：I-DISC 被违反的判定**不是低质量判定，是不可用判定**——把它当作普通低置信处理，等于让违反 I-DISC 的结果进入 SM1 统计，而 SM1 是 BOM 的核心指标。这是 AC5 的运行时落点，不只是测试项。

## 五、L2 · 1.7 journal 派生重算链（**挂账 3 的收口**）

### 5.1 三级可重算性分级（本节的地基）

| 级别 | 成员 | 定义 | 补偿手段 |
|---|---|---|---|
| **一级派生** | session-log 当前行 · 下一步指针 · 统计量 · 能力画像快照 · 错题与修复标记 · T2 补判索引 | **全部是 `journal.jsonl` 的纯函数** | 冷启动全量重算 → 必然自愈 |
| **二级派生** | chunk-ledger 调度栏（下次调度 / 状态迁移） | 依赖一级派生 + chunk-ledger 事实栏 | 重算；但**前提是事实栏与派生栏分栏**（见 5.4 缺口） |
| **不可派生** | corpus 材料/标注/音频 · queue 练习项/锁记录 · error-book 的「我写的 / 母语者会写 / 差别」 | 事实或半事实，无上游可算 | 只能靠 git / 备份，**重算救不回来** |

这张分级表决定了下面每一步的补偿策略：**能用重算兜底的，就不要写重试逻辑**——重试逻辑本身是会出错的第二套状态机。

### 5.2 触发时机 / 失败补偿 / 幂等性（卡内契约 3 的直接回答）

| 派生量 | 触发时机 | 失败补偿 | 幂等性 | 为何这样定 |
|---|---|---|---|---|
| **下一步指针** | **每轮 append 成功后同步执行，必须在 append 返回成功之前完成** | append 失败 → 指针不更新（本轮作废，损失上界 = 1 轮，AC2 成立）；指针写失败 → 标记 D3 脏 + 记 as-of，冷启动重建 | **天然幂等**：指针 = f(最后一个 `DD107 ≥ 1` 的行)，纯函数。⚠️ **不是 f(尾行)**——批次 7 已定 B0 追加 `DD107=0` 的会话级行且不推进指针；指针若取尾行，一次 B0 纯听就会把续学点冲掉 | 指针是续学点，延迟更新等于对学习者撒谎；同步执行使其不依赖任何后续流程 |
| **session-log 当前行** | **每轮**（微落盘，非会话末） | 失败 → 标 D6 脏 + as-of；**不重试**，下一轮或冷启动全量重算 | 幂等：会话聚合 = f(该会话全部轮次) | 重试会产生「写了一半的行」，比不写更难恢复；重算比重试可靠 |
| **统计量**（仪表盘四层） | 会话末 + 周报前 | 失败 → 不阻断会话，标统计陈旧 + **显示 as-of 时刻** | 幂等（聚合运算） | 统计晚一拍无害，陈旧但已标注无害；未标注的陈旧就是死法 A10 的变体 |
| **能力画像快照** | **每 N 轮 / 会话末批量**，非每轮 | 失败 → 沿用旧快照；G4 的 14 天新鲜度规则自动接管 → 编排退兜底包 | 幂等：画像 = f(判定历史) | 每轮产快照会让画像数随轮次线性膨胀，**SM5 的「近 4 周斜率」将不可读**——批量是 SM5 可用性的前提 |
| **错题与修复标记** | 每轮判定后 | 失败 → 标 D7 脏 + **报警**（不静默重试） | 幂等（按判定 ID 去重） | 错题丢失 = org-design §六.1 的核心指标「错题修复率」失真，且失真是**静默**的（比例会变得好看） |
| **T2 补判索引** | 每轮 | 失败 → 无需补偿：下一轮或 E-10 会**全量重扫 journal 自动补齐** | 幂等（集合重建） | 这是自愈性最强的一环——它证明了「派生 = journal 的纯函数」这个设计能兑现 |
| **B0 会话级行**（`DD107=0`） | B0 会话结束时 append 一行 | 同上（含在 journal 全量重算内） | 幂等 | ⚠️ **本层与批次 7 的交叉点**：该行 `DD108`/`DD109` 为空，**不产判定**。故补判索引的扫描谓词必须显式排除 `DD107=0`——否则空判定级别会被「≠T2」条件误捕，把每次 B0 纯听都当成待补判项 |

### 5.3 全量 vs 增量

**本图定：全量与增量两条路径必须产出相同结果，冷启动走全量。**

理由：本项目 journal 规模 = 每轮 1 行 × 每天约 10 轮 × 一年 ≈ **3–4 千行**，全量重算是毫秒级到十毫秒级。**为一个千行文件做增量优化，会引入「增量路径与全量路径不一致」这一整类难查 bug，而收益是零。** 若将来规模量级变化（多学习者 / 十万行级），再引入增量索引——但那时必须保留一条全量重建通道用于校验。

### 5.4 本层暴露的字段级缺口

⚠️ **`chunk-ledger.md` 必须拆「事实栏 / 派生栏」**才能支撑二级派生重算。当前该文件把 `状态(生/半熟/自动化)` 与 `下次调度` 写在同一行（org-design §七 模板），两者一个是派生、一个是派生的派生，混栏则：

- 合账时无法只保事实、只重算调度 → 挂账 2 的算法**没有字段落点**；
- 调度算法改版后无法区分「旧算法算的调度」与「新算法算的调度」。

**需要的三个新字段**（`语块` 对象目前属数据字典「未展开的 14 个对象」，字段完全未定义）：

| 字段 | 作用 | 若缺失的后果 |
|---|---|---|
| `调度结论来源` | 记录「本行调度结论由哪一侧产生（本地 / 设备 X / 合账重算）」 | 合账时无法做 OR 并集，只能回到 LWW——即退回原缺陷 |
| `调度算法版本` | 记录调度算法版本 | 两端算法版本不同时，「重算」用哪一版不确定，重算结果不可复现 |
| `合账脏标记` | 标记「事实已变、调度待重算」 | 重算失败后无法察觉，账本带着过期调度静默运行 |

→ 已列入本批 `cross_doc_fixes`，由编排者串行应用至 `03-data-dictionary.md`。

## 七、L2 · 1.9 跨设备合账（**挂账 2 的收口**）

### 7.1 裁决：本图定义合账算法

> 接口表 §五 给出的是「`chunk-ledger.md` 行级 LWW」，§八.1 已自陈「⚠️ 允许静默丢弃一方的风险，与『宁可重复不可丢失』冲突」，并把裁决移交本批。
> app-design §八 早已写明「chunk-ledger 行级 LWW **+ 记忆官幂等重算调度**」——即**既有设计意图本就是「重算」**，接口表只记了前半句。本图据此收口，并把它变成可实现、可测试的算法。

### 7.2 算法：调度信号 OR 并集 + 纯函数重算

```
1.9.1  同步⊘     检出账本目录变更 ⟨E-8⟩ / 兜底轮询（间隔 ≥5 分钟，拟案）
1.9.2  教练核心   拉取对端账本副本（整目录，不只冲突文件）
1.9.3  教练核心   合并 journal：并集，按 <交互轮次.轮次 ID> 去重
        └─ append-only 天然可交换，无序；同 ID 内容不一致 ─► 取更新时间较新者 + 留痕
1.9.4  教练核心   合并 chunk-ledger 【事实栏】：并集（同语块行的首遇/复现史取并）
1.9.5  教练核心   合并 chunk-ledger 【调度信号】：两方「应复习」取 OR
        └─ 写 <调度结论来源> = 合账；置 <合账脏标记> = 待重算
1.9.6  记忆官    重算 chunk-ledger 调度栏 = f(事实栏 ∪ 一级派生, <调度算法版本>)
        └─ 清 <合账脏标记>
1.9.7  教练核心   重算一级派生（指针 / session-log / 统计 / 画像 / 错题修复标记）
1.9.8  教练核心   原子写回（临时文件 + rename），更新同步游标 → 置「已同步」
```

### 7.3 为什么不用 LWW（三条论证）

| # | 论证 | 后果推演 |
|---|---|---|
| **A1** | **LWW 丢弃的不是事实，是派生结论**。`下次调度时刻` 由「语块复现史 + 记忆官算法 + 距上次间隔」算出，是**两个不同算法版本、两个不同输入快照的产物**。用一个派生产物覆盖另一个派生产物，丢掉的语义是「其中一方认为该复习了」 | 若 LWW 采信设备 A（较早算出）的调度，覆盖设备 B 刚刚写入的「该复习」信号 → 记忆官少调度一次 → **死法 A3 的队列断供以「静默少练」的形式出现**，且仪表盘完全看不出异常 |
| **A2** | **OR 并集是唯一不丢信息的合**，且代价极低：个人语块量级千级，OR 操作 O(n)，可忽略 | 相比之下 LWW 省下的计算量是**零**（重算是一次纯函数调用，见 A3） |
| **A3** | **重算是纯函数 ⇒ 合账天然幂等**。`f(事实, 版本)` 是确定性的，同输入必同输出，因此「合账后重算」不需要任何幂等键、去重表或版本比对 | 若改为「采信任一方的调度」，则必须为调度结论引入时间戳仲裁规则，反而**新增**了一类需要保证幂等的状态 |

### 7.4 失败与状态一致性

| 失败点 | 处置 | 同步游标状态 |
|---|---|---|
| 1.9.3–1.9.4 合并冲突不可自动消解 | 挂起 + 展示冲突项供人工裁决 ⟨07-DT §四⟩ | **「同步失败」**（第四态） |
| 1.9.6 调度重算失败 | `<合账脏标记>` 保持为真；**不得清标记** | **「同步中」不得改为「已同步」**——账本尚未一致，谎报已同步即死法 A10 |
| 1.9.7 一级派生重算失败 | 标脏 + as-of；下一轮冷启动全量重算自愈 | 同上 |
| 1.9.8 写回中断 | 临时文件残留，不影响原文件（原子 rename 保证） | 「同步失败」，下轮自动重试（**重试不提升状态**） |

⚠️ **新增约束（与 04-state-table §八 一致）**：「合账 + 重算」必须视为**一个原子步骤**。重算未完成时同步不得离开「同步中」——这与状态表已定的「自动重试不提升状态」是同一条纪律的延伸。

⚠️ **本节的落地前提**：算法依赖 `03-data-dictionary.md` 尚不存在的三个字段（见 §5.4）。**字段未补齐前，本算法不可实现**——这是本批给编排者的硬前置。

## 八、L3 · 1.4 B0 档 TTS 失效降级链（**挂账 1：只给方案与代价，不裁决**）

### 8.1 问题陈述

生态图 §4.2：**B0 档完全依赖音频，却是四档中场景最广的一档**（做饭 / 走路 / 通勤）。现有设计只有「本地引擎为基线」一句，**没有失效路径**——失效只能在唤起那一刻被学习者发现，而 B0 队列看起来是「满的」。

### 8.2 本图可自行确定的部分（不涉及 B0 的定义，不越界）

| # | 处置 | 理由 |
|---|---|---|
| **E-1** | **音频纳入 B0 档练习项的准入门槛**，与「材料 ≥1 标注」「细则非空」同级 | 与既有准入门槛同机制同层级，不改变任何定义（DFD L2-2.5 已落） |
| **E-2** | **失效发现时机从「唤起期」前移到「补切期」** | 这是生态图 §4.2「没有失效路径」的真正病根——不是缺降级，是缺**可观测性**。补切期失败即可见，唤起期才不至于被打断 |
| **E-3** | **B0 档水位线要求升级为「≥2 个音频齐备的可取项」** | 原水位线「≥2 项」未区分音频齐备，导致水位虚高 |
| **E-4** | **音频生成失败必须留痕**，不得静默计入水位 | 同上：没有留痕就等于把失效藏起来，即死法 A10 的形态 |

**注意**：E-1…E-4 只回答「什么时候知道坏了」，**不回答「坏了之后 B0 变成什么」**——后者是定义问题。

### 8.4 裁决轴（本图能给出的唯一判断依据）

四个方案的分野不在技术，在**「B0 的定义锚是什么」**：

```
              B0 = 「零交互轮」（形态锚）
                    ├──→ 方案 A（如实告知，形态不变）
                    └──→ 方案 B（形态可变，接受它变成 B2）

              B0 = 「手眼被占用的碎片场景」（场景锚）
                    ├──→ 方案 C（场景内无音频的形态）
                    └──→ 方案 D（把场景锚正式写进契约）
```

**这个轴本身是产品命题**——B0 是「零交互轮」还是「通勤场景」取决于产品希望学习者如何理解四档，属于 goal-keeper 的定义权，**不是流程建模能替你回答的问题**。本图只把四条路的代价摊开。
