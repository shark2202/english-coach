## 〇、复核方式（本文可信度来源）

本文 v1 由主会话单线产出。v2 经**三路独立判别器**复核，三者写域隔离、只读、互不通气：

| 镜头 | 范围 | 判定 |
|---|---|---|
| 事实核验 | 外部断言 vs 一手来源（npm / 官方博客 / GitHub API） | **FAIL**——2 条事实错误 + 1 条计数违规 + 3 条时效失准 + 可追溯性缺失 |

| 逻辑核验 | 推论有效性与仓内一致性 | 主结论站不住反面，但**降级过头 1 处、自相矛盾 1 处、越权 3 处、前提错误 1 处** |

**已作废的 v1 结论**：A11「已消解」、「固定 5 项原生冒烟清单」、「改用 SFC 内 `<style>`」、
「预览快 2 倍」、「把快速预览从选择理由降格为副产品」。详见 §七。

## 一、结论（修正版）

**1. 选型成立，无需推翻。** 四端一级平台、双产物（一套源码 → lynx + web bundle）实测成立；
桌面渲染能力的关键疑虑（CSS 覆盖、键盘事件）经一手来源与实测双向证实，**确属高估**。

**2. 但「快速预览」没有入册。** `app-design.md` 全文 `预览`/`HMR`/`热更新`/`调试` **零命中**——
它不是仓内的裁决理由，只出现在 goal-keeper 的口头提问中。**因此本文不「降格」它，而是建议：
要么补记进设计文档并注明其为事后追认、要么根本不入册**，以免日后被当作既有理由重新发现。

**3. 真正的难点不在预览回路。** 本产品难处在 `coach_core`（账本契约、append-only journal、
记忆官调度、离线三级判定）与 **L4 原生集成**（后台音频锁屏控制、Handoff、Widget、全局热键）——
这些在浏览器预览里**一件都验不到**；而 UI 本身很薄。

**4. 两个口径必须分开。** v1 把「是否约束成败」和「是否具竞品判别力」混成一列，导致
「预览回路不是瓶颈」与「预览回路应置顶为首要判据」自相矛盾。v2 在 §二 拆成两列。

## 二、判断基准三问

### 可行吗

**分层可行**（不宣称端到端已验证——对齐 [AGENTS.md](../AGENTS.md) S8 分层诚实）：

- ✅ **组装层成立**：工具链跑通、双产物成立、本产品真实 UI 约束（三栏 / 衬线 / 34em 行宽 /
  行内词汇标注 / 会话流）在 Web 预览全部渲染正确。
- ⚠️ **原生层未验证**：Web 预览 ↔ 原生渲染保真差**未实测**，这是当前最大未知。

### 维度（**两个口径分列**）

| 维度 | 评级 | 是否约束成败 | 是否具竞品判别力 |
|---|---|---|---|
| **L4 原生集成深度** | 🔴 弱项 | **是** | 强（Flutter 插件生态更厚） |
| **`coach_core` 可测性** | 🟢 强 | **是** | 弱（任何栈都一样） |
| **上游优先级漂移（A11 机理之一）** | 🟡 中 | **是** | 弱（不可控项） |
| 预览/调试回路 | 🟢 强（样式改动除外） | 否 | **待验证假设** ⚠️ |
| agent 无头可验证性 | 🟢 强 | 否 | **待验证假设** ⚠️ |
| 桌面渲染能力 | 🟢 优于 v1 判断 | 否 | 中 |
| 桌面宿主 / 组件生态 | 🟡 中 | 否 | 弱 |
| Linux 覆盖 | 🔴 无 | 否 | — |

> ⚠️ **「agent 可无头验证是结构性差异」目前是待验证假设，不是已证结论。**
> 本次未对任何对照方案（Vue+Vite / Tauri / Flutter）做同类测量，无一条对照数据。
> 该假设要么在 Phase 1 前期补测，要么不得作为选型判据使用。

### 死法

**A11（Lynx 生态早期叠加）—— 显著下调，但未消解。**

- ✅ 下调部分：「Vue×桌面能力缺口」这一机理被一手来源证伪（CSS 覆盖 97%、桌面键盘事件完整）。
- ❌ 未消解部分：「**平台路线随上游优先级漂移**」（`app-design.md:206` 原文机理）**未获任何新证据**。
  本文证据全部是渲染能力证据，与该机理不对口。
- 📌 **触发条件继续进周报**：VueLynx 桌面 Beta / Lynx 平台列表变动。

**N1（样式热更新缺口）—— 成立，见 §三 F4。**

### 可逆性

**依旧极高，不变。** 账本契约先行 + `coach_core` 纯 TS + Flutter 回退 + CLI 壳，三重保险成立。
框架选错的最坏后果仍是「重写壳层，进度零损失」。

## 四、建议（**全部上交，本文不执行**）

### 4.1 关于「快速预览」这条理由

**建议 goal-keeper 裁定其一**：① 补记进 `app-design §三`「主选的真实收益」并注明系事后追认；
② 不入册。理由：它从未构成裁决依据，若入册而不标注，会被误读为当初的决策基础。

### 4.2 关于判据

若 4.1 选①，建议新增一条并**与瓶颈判据分列**（不混为一谈）：

> **一套渲染模型同时服务于预览与四端原生 + 原生渲染（非 WebView）+ 预览页可被 agent 无头验证。**

⚠️ 其中「agent 可无头验证」部分**尚无对照测量**（见 §二），建议标注为待验证假设。

### 4.3 关于投入顺序

| 优先级 | 建议投什么 | 理由 |
|---|---|---|
| P0 | `coach_core` 纯 TS + vitest 无头全量测试 | 真正的快反馈杠杆，且**与选型无关** |
| P1 | **AC 的原生侧按节奏执行**（非新增清单） | 见下方撤回说明 |
| P2 | 壳层 UI 迭代 | 收益递减区 |
| P3 | 补「Web 预览 ↔ 原生保真差」实测 | 当前最大未知 |

> **撤回 v1 的「固定 5 项原生冒烟清单」。** 该五项与 `app-design §十` AC 1/2/6/7/9 完全同义，
> 等于把 **11 条验收门压缩为 5 条**，并打断 `requirements/17-use-case.md` 中依赖 11 条 AC 的对应矩阵。
> **缩减或改写 AC 属 goal-keeper 裁决，不由本文代决。**
> 正确表述是：AC 数量与内容不变，仅建议其**原生侧执行方式**从「验收时跑」改为「按节奏跑」。

### 4.4 关于样式热更新缺口（N1）

**❌ v1 的对策「改用 SFC 内 `<style>` 块」经实测为假**——该写法同样不热更新。

当前**唯一未被证否**的路径是 inline `:style` 属性绑定（走 JS 通道，而 JS 通道热更新已实测成立）。
但此路径**未经直接实测，属推断**，接入前须先验一次。
