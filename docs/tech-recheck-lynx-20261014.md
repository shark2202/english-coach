# Lynx 选型复核——「快速预览」这条理由成立，但它不是瓶颈轴

> **问题**：当前选 LynxJS，考虑的是它能快速预览、调试——这是加快正向反馈、迭代的重要特性。
> 深度调研 + POC 落实之后，它还是本项目的最优选择吗？

> **本文定位**：补上 [tech-eval-lynx](tech-eval-lynx-20261014.md) 自陈的「未实测」缺口。
> 原始评估结论（Flutter 主选）已被 v0.3 goal-keeper 裁决推翻，三项顾虑转为已接受风险；
> 本文**不动摇裁决本身**，只检验裁决所依据的理由是否成立、是否被放在了正确的位置。
> 可复现工程 [poc/](../poc/README.md) · 原始测量 [poc/evidence/measurements.md](../poc/evidence/measurements.md)。

---

## 一、结论先行

**裁决理由成立，选型不必推翻；但判据要换，赌注要重分配。**

三层结论：

1. **「快速预览」是真的，且比原评估记录的印象更强。** 实测：Web 预览重建 **0.15 s**、
   JS/模板改动**不刷新即更新**、预览页可被 agent **无头验证**（a11y 快照 / 截图 / 计算样式探针）。
   原评估称「Vue×桌面双早期」，实测到的桌面数据远没那么糟（CSS 覆盖 97%、Lynxtron 0.0.28 月度迭代、
   官方 DevTool MCP + Agent Skills）——**风险高估了**。

2. **但它不是本项目的瓶颈轴。** 这个产品难的地方在 `coach_core`（账本契约、append-only journal、
   记忆官调度、离线三级判定）与 **L4 原生集成**（后台音频 + 锁屏控制、Handoff、Widget、全局热键）。
   这些**在浏览器预览里一个都验不到**；而 UI 本身很薄（会话流 + 阅读 + 播放），
   预览快 2 倍不改变成败。**为「更快」付出的代价（宿主自建、Alpha 生态）买到的不是瓶颈。**

3. **若以预览速度为唯一判据，Lynx 也不是最优。** 实测**纯 CSS 改动不热更新、需手动刷新**
   （见 §三 F4）——而这恰恰是 agent 调样式最频繁的操作。普通 Vue + Vite 在该维度更快。
   Lynx 真正的成立理由应改挂：**一套渲染模型同时覆盖预览与四端原生 + 原生渲染（非 WebView）+ agent 可验证回路**。

**给 goal-keeper 的一句话建议**：保留 LynxJS，但把「快速预览」从**选择理由**降格为**副产品**，
把 Phase 1 的迭代预算投向 `coach_core` 与一份固定的原生冒烟清单，而不是投向壳层预览体验的继续优化。

## 二、判断基准三问

### 可行吗

**可行，且比 v0.3 裁决时的证据更充分。** 四端一级平台成立；桌面不再是需要赌的早期切片；
双产物（一套源码 → lynx + web bundle）实测成立；本产品真实 UI 约束（三栏 / 衬线 / 34em 行宽 /
行内词汇标注 / 会话流）**全部渲染正确**。

### 维度（按「是否约束成败」重排，而非按「好不好」）

| 维度 | 评级 | 是否瓶颈 | 说明 |
|---|---|---|---|
| **L4 原生集成深度** | 🔴 弱项 | **是** | 后台音频锁屏控、Widget、菜单栏、全局热键、Handoff——无 Flutter 式插件生态兜底，自写量未知（未实测） |
| **`coach_core` 可测性** | 🟢 强 | **是** | 纯 TS、零 UI 依赖，vitest 可无头全量覆盖——**与选型无关**，任何栈都一样 |
| 预览/调试回路 | 🟢 强（但 CSS 需刷新） | 否 | 实测优秀，见 §三；但 UI 薄，收益递减 |
| agent 可验证性 | 🟢 强 | 否 | 浏览器预览可被 agent 驱动；官方还在补 DevTool MCP |
| 桌面成熟度 | 🟡 中上 | 否 | CSS 97% / 元素属性 73%；`lynx-ui` 组件集暂不含桌面 |
| 生态成熟度 | 🟡 中 | 否 | `create-vue-lynx` 仍 0.1.x；运行时不在官方 npm scope |
| Linux 覆盖 | 🔴 无 | 否 | 已由 v0.3 裁决显式延后/取消 |
| 性能必要性 | ⚪ 无 | 否 | 会话流+阅读，无性能理由（与原评估一致） |

### 死法

**已消解一条**：原死法「押 macOS 却落在 Vue×桌面早期切片」——实测桌面 CSS 97%、键盘事件完整、
Lynxtron 在迭代，此风险显著下调。

**新增一条（N1）—— agent 样式迭代摩擦**：纯 CSS 改动不热更新。agent 构建 UI 时改样式是高频动作，
每次都要多一次手动刷新。量级不大（构建 0.12 s + 刷新 ~1 s），但会让 agent 的「改-看」循环出现固定毛刺。
对策：迭代期把可变样式走 inline `:style` 绑定（模板原生支持），或接受刷新。

**未消解一条**：L4 原生自写量（A12）仍是最大未知，且无法靠预览回路证伪。

### 可逆性

**依旧极高，不变。** 账本契约先行 + `coach_core` 纯 TS + Flutter 回退路径 + CLI 壳，
三重保险在本次复核后依然成立。框架选错的最坏后果仍是「重写壳层，进度零损失」。

## 四、建议：判据换挂，投入重分配

裁决不变，但把理由和资源摆到正确的位置：

### 4.1 判据换挂

`app-design §三` 中「主选的真实收益」目前列的是单语言栈 + Web 亲和 + 桌面同栈 + CLI 复用。
建议**新增一条并置顶**：

> **一套渲染模型同时服务于预览与四端原生 + 原生渲染（非 WebView）+ 预览页可被 agent 无头验证。**

理由：前几条 Flutter/ReactLynx 都能部分满足，只有「agent 可无头验证的预览回路」
在 agent 蜂群构建模式下是**结构性差异**。而这正是本仓的既有组织形态（见 [swarm/ORG-SPEC.md](swarm/ORG-SPEC.md)）。

同时**下调**「快速预览」：它是真的（实测 0.15 s），但它是这套选择的**副产品**，不是选择的首要理由。
理由一旦被写进设计文档，日后遇到更好的选项时就会成为不必要的沉没成本。

### 4.2 投入重分配

| 优先级 | 投什么 | 为什么 |
|---|---|---|
| **P0** | `coach_core` 纯 TS + vitest 全量无头测试 | 真正的快反馈杠杆在这里，且**与选型无关**——先把它做完，UI 栈就变成可随时替换的薄壳 |
| **P1** | 一份**固定 5 项原生冒烟清单**（后台音频锁屏控 / Handoff 接力 / 冷启动 <2s / 杀 App 续学 ≤1 轮 / 账本目录人工可读） | 把 L4 从「持续设备迭代」变成「按节奏跑的检查项」，避免被预览回路的顺畅感掩盖 |
| **P2** | 壳层 UI 迭代 | 收益递减区。够用即可，别为预览体验本身投入 |
| **P3** | 桌面原生热更新回路的实测（Lynx Explorer / Lynxtron 跑一次） | 补 §五 残余不确定性 |

### 4.3 一条立即可做的规避

迭代期把**高频变动的样式走 inline `:style`**，绕开 F4 的 CSS 热更新缺口；
等界面定型后再回落 class + CSS 文件。

## 五、残余不确定性（务必如实计入）

| 项 | 状态 | 为什么重要 |
|---|---|---|
| **Web 预览 ↔ 原生渲染保真差** | ❌ 未实测 | 本产品是**长文阅读**，对换行点/行高/字体度量敏感。浏览器好看 ≠ iPhone 好看——**这是当前最大的未知** |
| Lynx Explorer 原生预览的热更新回路 | ❌ 未实测 | Phase 1 主战场的真实开发体验 |
| Lynxtron 实际运行 | ❌ 未实测 | macOS 壳目前只有文档级证据 |
| L4 原生宿主实际自写量（A12） | ❌ 未实测 | 最大成本未知项 |
| Android / Windows | ❌ 未实测 | Phase 2 |

**建议触发条件**：Phase 1 开工后，前两周内把「Web 预览 ↔ 原生保真差」与「Lynxtron 实跑」
各做一次，用真机/真桌面出结论。若保真差不可接受，这就是提前止损的信号——
而不是等到 Phase 1 中途才发现。
